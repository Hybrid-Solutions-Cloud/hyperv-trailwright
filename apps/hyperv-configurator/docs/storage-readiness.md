# Physical storage and SAN readiness

Version 0.23.0 · project schema 20 · assessment contract 0.1.0. Primary references reviewed 2026-09-11.

Storage systems retain separate logical capacity, physical footprint, volume lifecycle and resource-disk allocations. The new readiness model adds device eligibility and actual initiator relationships to that existing calculation. It does not execute storage commands.

Each physical drive group records connection and controller presentation, shared-host/multipath access, flash power-loss protection, native device identities, driver/certification and dated evidence. Boot devices remain separate from S2D capacity/cache. Explicit SAN/shared/virtual connections, RAID virtual disks, shared access/MPIO or unavailable flash protection make a physical S2D pool device incompatible. Capacity and cache incompatibility leave physical inventory and repair/headroom estimates unknown. Missing observations remain review-required; an operator-reviewed device remains runtime unqualified.

The dated Windows Server hardware review includes 400 TB per-server and 4,000 TB pool ceilings. Capacity drives alone exceeding the node ceiling trigger a finding. The cache metadata allowance is reported separately at 4 GB per TB of cache, in addition to OS/VM/application demand. These hardware units are decimal; entered drive and pool quantities remain binary GiB/TiB. The allowance is not a complete host-memory sizing result. [Microsoft S2D hardware requirements](https://learn.microsoft.com/en-us/windows-server/storage/storage-spaces/storage-spaces-direct-hardware-requirements).

One storage-interface record represents one physical initiator port. FC interfaces retain WWPNs, HBA/slot identities and fabric evidence independently of Ethernet inventory. iSCSI interfaces link to their host's Ethernet adapter and reviewed storage network. SAN routes link to interfaces and volumes, and retain target identity, observed path state and independent-path acceptance. Duplicate WWPNs, host/protocol mismatches, incompatible transport networks and impossible/future observations remain visible. Two route labels through one initiator do not establish physical path independence. [Microsoft cluster storage architectures](https://learn.microsoft.com/en-us/windows-server/failover-clustering/storage-architectures).

Backend action and owner distinguish preservation, creation, expansion and replacement. Existing identity/baseline and replacement migration approval/window are explicit. Resource disk attachments identify one host, an intended cluster, or an externally reviewed provider. Node-local storage cannot be assigned to another host or treated as shared cluster storage. Shared storage attachments must match the owning backend cluster.

Schema 19 projects migrate with these answers unset and no fabricated interface records. Sanitized sharing remaps interface, route and attachment references and removes native identities/evidence. The shared assessment feeds storage validation, the physical eligibility panel, `plans/storage-readiness.json`, storage Markdown, generic PDF inventory, **Physical storage review** workbook/CSV, complete storage YAML and interface/route topology.

Coverage is in `src/storageReadiness.test.ts` and `e2e/storage-readiness.spec.ts`: eligibility, cache versus boot roles, decimal limits, metadata allowance, preservation/replacement, FC/iSCSI identity and ownership, correlated physical routes, local/shared attachments, strict timestamps, migrations, deterministic ordering, sanitization and actual browser correction/save/open/download. Full release regression and artifact inspection remain required before publication. Native pool changes, MPIO configuration, path failure/recovery and storage acceptance require their selected consumers and separately authorized environments under implementation-plan H.
