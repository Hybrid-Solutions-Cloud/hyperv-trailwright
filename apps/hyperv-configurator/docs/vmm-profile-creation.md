# VMM physical-computer profile creation

The Configurator keeps a desired profile separate from an existing VMM object. Select VMM BMC / PXE and Define a new profile in Hosts and provisioning. Complete the creation fields, associate the generalized image artifact and assign the intended physical hosts. Review findings through their field links.

The package contains `handoffs/vmm-profiles/plan.json`, this guide and `reports/vmm-profile-creation.md`. The JSON binds the handoff to a project ID, revision and stable profile record IDs. This package contains configuration data and reports, with no deployment scripts. No resolved credentials are exported. A complete handoff has status `design-handoff`; this does not mean automation-ready or deployed. An existing profile reference must identify the reviewed VMM object.

## Operator workflow

1. Confirm the named VMM service, installed VMM/module versions and authorization for profile creation. Check the library for a conflicting profile name. Do not overwrite or adopt an existing object by matching its name.
2. Resolve the VHD/VHDX library GUID and compare its path, version and SHA-256 with the selected media artifact. Review generalization, guest release/install type, firmware, drivers and servicing. Source and checksum are design inputs until verified against the actual artifact.
3. In the VMM library's physical computer profile workflow, create a VM host profile. Select the reviewed image and conversion policy. Configure the reviewed physical NIC profiles, OS disk layout, driver selection and membership. Retain the exact settings and command generated by the selected VMM build as qualification evidence.
4. Resolve the local administrator credential at runtime through the responsible runner/operator. Resolve Run As accounts and NIC profiles by their exact GUIDs on the named VMM service. Review CDN/MAC matching, management address allocation, logical switches/uplink profiles and per-host applicability. A NIC profile GUID alone does not demonstrate a correct mapping. Review the computer OU/prestaging separately from the domain FQDN. Explicitly choose Plug and Play or tag-based driver matching; a selected driver package requires a pinned artifact and publisher/signature review.
5. Review disk targeting, boot/system partitions, filesystem allocation units and data-disk preservation for every assigned host. The form detects a partition-style mismatch, but does not parse or qualify VMM's complete disk string grammar. Do not paste a generic layout onto unreviewed hardware.
6. Create the profile only within the separately authorized environment. Capture the returned GUID and read back its image, network, membership, driver and disk settings. Record the observed settings and acceptance evidence in the responsible implementation stage. A profile creation result does not authorize any host reimage.
7. After this review, change the same design profile to Use existing profile and enter the returned GUID in Existing profile reference. The creation answers remain available if needed; saving produces a new project revision. Re-export and review the bare-metal target plan before separate host authorization.

## External VMM configuration mapping

These reference mappings describe the existing VMM `New-SCPhysicalComputerProfile` configuration model. Your implementation team can use them to map the design into its existing tooling. The configurator produces no executable code.

| Handoff input | Cmdlet binding / review |
| --- | --- |
| `name`, `vmmServer` | `Name`; resolve the service connection for `VMMServer` |
| `virtualHardDisk.id` | Resolve the library VirtualHardDisk object for `VirtualHardDisk`; verify the associated artifact first |
| VM host purpose | `UseAsVMHost` |
| Domain membership | `Domain` and the resolved `DomainJoinRunAsAccount` |
| Workgroup membership | `JoinWorkgroup`; do not also bind domain parameters; review management and cluster support separately |
| `localAdminCredentialRef` | Resolve externally for `LocalAdministratorCredential`; never serialize the credential into this handoff |
| `membership.computerAccessRunAsId` | Optional resolved `ComputerAccessRunAsAccount` |
| `networkAdapterProfileIds` | Ordered resolved `PhysicalComputerNetworkAdapterProfile` objects, with the separate mapping review |
| `storage.diskConfiguration` | Reviewed `DiskConfiguration` string; no inferred partition grammar |
| `storage.bypassVhdConversion` | Explicit `BypassVHDConversion`; false requests fixed conversion, true retains source allocation type |
| `storage.vmPaths` | Ordered paths joined with the documented pipe delimiter for `VMPaths`; embedded pipe characters are rejected |
| `drivers.matchingTags` | Optional `DriverMatchingTag` list; verify package applicability independently |
| `answerFile.id` | Optional resolved library Script object for `AnswerFile`; verify reference and SHA-256 and inspect contents for secrets |
| `os.timeZoneId` | Explicit numeric `TimeZone`, including zero; verify the selected build's time zone mapping |

Locale, activation method, hardware applicability and acceptance remain review inputs. No literal product key, arbitrary post-install command or secret-bearing answer file is embedded. Review that the existing implementation process represents every selected setting.

## Preservation and migration

Project schema 8 adds the creation inputs with empty values when opening schema 7 or earlier. It never invents Run As IDs, image identities, disk settings, credential references or a returned profile ID. Existing profile references retain their saved values. Shared exports scrub free-text object IDs, endpoints, paths and references and therefore cannot be used operationally.
