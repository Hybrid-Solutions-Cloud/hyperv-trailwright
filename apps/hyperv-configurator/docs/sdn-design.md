# Hyper-V SDN design and setup

SDN scope (none, existing, new, expand) and delivery intent (design, handoff, use existing external automation) are separate choices. The configurator produces SDN configuration and implementation checklists without an execution adapter. Generating a package never changes infrastructure or records a successful stage.

Specify the controller architecture, exact OS/tool versions, setup owner and fabric identity. Bind management/HNV/VIP networks, REST address and DNS name, client MAC pool, domain/service/deployment/certificate identities, VM media/storage and compatibility evidence. Existing fabrics require native identity and a preservation baseline; expansion also requires exact change scope. Prior schema notes survive migration, but new choices and identity bindings remain unanswered.

Each SDN resource, BGP peer and tenant service has one lifecycle owner. Existing objects require a native identity and baseline. Duplicate identities, conflicting change owners, replacement, and changes under use-existing scope are blocked. Each participating host has one binding to its actual host switch, provider network and prerequisites. The host binding describes readiness requirements; it does not attest that a prerequisite ran.

Capabilities derive required controller, MUX and gateway roles from both fabric selections and tenant services. Host controller CPU/memory/disk allowances, controller VMs, and MUX/gateway VMs have separate schedules. Enter exact host/cluster placement, failure domains and positive capacity. No role sizing is invented.

The reviewed FCNC baseline uses a Windows Server 2025 failover cluster with at least two nodes, shared storage and host prerequisites. Record one overhead allowance and host binding per controller node. Microsoft documents host roles, restart, AD membership and consistent switching as prerequisites. [FCNC deployment](https://learn.microsoft.com/en-us/windows-server/networking/sdn/deploy/deploy-network-controller-failover-clustering).

VMM controller handoffs require the owning VMM service and exact controller service-template, logical-network and logical-switch identities. The VM service-template path does not establish support for VMM managing FCNC; that combination retains an explicit compatibility review. [VMM controller deployment](https://learn.microsoft.com/en-us/system-center/vmm/sdn-controller?view=sc-vmm-2025).

`plans/sdn-design.json`, `environment/sdn.yml`, `reports/sdn-design.md`, the PDF, workbook and CSV schedules share one assessment. Ordered stages cover prerequisites, hosts, controller, host networking, selected NFV, tenant services and acceptance. The contract lists isolation, east/west, north/south, VIP/NAT, BGP and failover scenarios when applicable. [Structured tenant policy, backend and gateway designs](sdn-services.md) are available in schema 25, including gateway budgets and explicit setup/acceptance targets. [Returned SDN acceptance evidence](sdn-evidence.md) can now be imported against the exact requested scope; scenario descriptions alone are not runtime tests or results.

SdnExpress 1.1.245 was inspected as a possible future external consumer, without executing it. Its configuration-file parameter evaluates file text; its `SkipDeployment` switch is not an offline execution guard. A future adapter must build validated in-memory configuration and own its read-only validation boundary. Do not run the vendor script to validate a package. The module is not redistributed here. [Pinned module](https://www.powershellgallery.com/packages/SdnExpress/1.1.245).

VMM gateway handoffs derive an SLB/MUX prerequisite even when the user selected only routed connectivity. Separate SLB, gateway and BGP stages preserve dependency order. Microsoft requires SLB deployment before VMM gateway setup. [VMM gateway prerequisites](https://learn.microsoft.com/en-us/system-center/vmm/sdn-gateway?view=sc-vmm-2025).

## Controller architecture decisions (0.31.0)

Choose a structured Windows Server release and numeric build, then a deployment tool and numeric version. Keep explanatory OS/tool text separately. The release selection describes the intended controller OS; host inventory remains an observation. An explicitly older observed host release calls for upgrade and fresh inventory review. Years in patch notes do not override the release decision.

Controller VMs support single, three-node, or custom topology and Generation 1/2. Controller-service redundancy is separate from highly available VM hosting. A three-node design requires distinct inventoried hosts/failure domains. Clustered VM availability requires at least two hosts in a failover cluster; independent hosting can use a standalone host group. A custom topology requires further compatibility review. Single controllers expose outage/recovery acceptance and use their management address once in the shared address allocator.

For VMM, select the dedicated host group, service template and logical network/switch IDs. Record the customized template hash and immutable source revision, local-admin/domain-management Run As IDs, and management/client AD security groups. The plan maps the documented single/three-node Generation 1/2 template filenames and selected parameter references. One-subnet multi-node deployments use a reserved REST IP; multi-subnet deployments use REST DNS. Single-node templates omit the unused RestEndPoint parameter. Review domain/group membership, SPN permissions and certificate resources before handoff. Resolve passwords at runtime; do not enter them in the designer. [VMM controller procedure](https://learn.microsoft.com/en-us/system-center/vmm/sdn-controller?view=sc-vmm-2025).

FCNC retains its two-node Windows Server 2025/shared-storage prerequisites. The reviewed tool minimums are SDN Express 1.1.231, or Windows Admin Center 2410 with SDN extension 3.6.0. These checks describe documented prerequisites; they do not qualify the selected binaries. VMM/FCNC still requires separate compatibility qualification. [FCNC prerequisites](https://learn.microsoft.com/en-us/windows-server/networking/sdn/deploy/deploy-network-controller-failover-clustering).

The plans/sdn-controller.json file contains the controller mapping, also embedded in plans/sdn-design.json. Architecture-specific fields appear in Markdown/PDF/workbook reports and environment/sdn.yml. Hidden answers remain in project saves but do not drive the active handoff or evidence fingerprint. Schema 27 leaves new decisions unanswered during migration. Evidence scope contract 2 deliberately invalidates older scope hashes; original observations remain preserved and need a fresh request before reuse.

Full native VMM/SDN Express consumers, certificate-resource bindings, exact tool/OS matrix qualification and executed acceptance remain open in the implementation checklist.
